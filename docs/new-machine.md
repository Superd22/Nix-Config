# Setting up a new Mac

Two situations, one document:

- **Migrating**: you have the old Mac in front of you and want the new one to
  be the same machine, then wipe the old one. This is the main path.
- **From scratch**: no old Mac (or a fork of this repo by someone else). See
  [From scratch](#from-scratch) at the end; everything else still applies.

Order matters. The keys have to be in place before the flake will even
evaluate, and one of them cannot be regenerated, so the migration path is
built around a single rule: **do not wipe the old Mac until `keys doctor`
passes on the new one.**

## The three keys

Everything on the laptop is either in this repo, in the private `nix-secrets`
repo, or regenerable, except three files. They are what fetches, decrypts and
commits to the secrets store, so they cannot live in it:

| File | Role | If lost |
| --- | --- | --- |
| `~/.ssh/id_rsa` | GitHub. The `secrets` flake input is `git+ssh://github.com/superd22/nix-secrets`, and `modules/programs/ssh.nix` pins github.com to this key with `IdentitiesOnly`. | The flake cannot fetch its inputs, so it does not evaluate. Replaceable: generate a new one and add it to GitHub. |
| `~/.ssh/id_ed25519` | The agenix identity. Its public half is the `david` recipient in `nix-secrets/secrets.nix`; `modules/secrets.nix` decrypts with it during activation. | **Every `.age` file is undecryptable forever.** Not replaceable without a machine that still holds it. |
| GPG key for the commit email | `modules/programs/git.nix` sets `commit.gpgsign = true`. No key id is pinned; gpg picks the secret key whose user id matches `mine.user.email`. | Commits are rejected until a new key is made and uploaded to GitHub. |

They are one identity that moves with you, not per-machine keys. Nothing on
GitHub or in `nix-secrets` changes when you change laptops.

`nix run .#keys` moves all three as one passphrase-encrypted bundle, and that
bundle doubles as the backup that survives both laptops dying. The script is
`apps/keys.sh`.

Not in the bundle, on purpose:

- `~/.ssh/id_ed25519_agenix`: generated by a long-deleted `create-keys` script.
  Despite the name it is **not** the agenix identity (its pubkey is not in
  `secrets.nix`) and nothing reads it. `doctor` warns while it exists. Delete it.
- `~/.ssh/self_deployment`: a deploy key referenced nowhere in this config.
  Revoke it when the old Mac is retired unless you know what it deploys.

## The short way: `bootstrap.sh`

Steps 2 to 8 below are what `bootstrap.sh` and the `init` wizard do. On the
new Mac, once the bundle from step 1 is on it:

```sh
curl -fsSL https://raw.githubusercontent.com/Superd22/Nix-Config/main/bootstrap.sh | sh
```

The stub installs the Xcode command line tools and Determinate Nix, then
hands over to `nix run github:Superd22/Nix-Config#init`, which is
`apps/init.sh`: it clones the config, settles the hostname (rename the Mac
after an existing host, or add `hosts/<name>` as a copy of one), runs
`keys import` on the bundle you pick, `keys doctor`, `build-switch`, and
prints the list from step 8. It stops at the first thing that fails and
never touches the old Mac. Re-running it is safe: an existing clone is
reused and keys already in place are left alone.

Every prompt can be answered from the environment (`INIT_HOSTNAME`,
`INIT_BUNDLE`, `INIT_DEST`, `INIT_YES=1` or `--yes`, `INIT_SKIP_BUILD=1`),
which is how CI runs it without a terminal. `nix run .#init -- --help` lists
them.

Step 3 lists every `keys-*.age` it can find in `~/Downloads`, `~/Desktop`, `~`,
the clone and any mounted volume, newest first, and offers a typed path when
the bundle is somewhere else. If the file is on an external disk that is not
mounted yet, or you would rather not answer the prompt at all, pass
`INIT_BUNDLE=/path/to/keys-<host>-<date>.age`.

The rest of this document is the same procedure by hand, and what to do when
a step fails.

## Migrating

### 1. On the old Mac: export

```sh
cd ~/.config/nixos-config
nix run .#keys -- export
```

It writes `keys-<hostname>-<date>.age`, encrypted with a passphrase you choose,
and prints a manifest with the fingerprints of what went in. gpg may ask for
the signing key's passphrase through pinentry.

Then, and this is the part that matters:

1. Move the file to the new Mac. AirDrop is fine; it is encrypted.
2. **Put a second copy somewhere that is not a laptop**: your password manager
   as an attachment, or an external disk. With this file and its passphrase you
   can rebuild from nothing. Without it, losing both laptops loses the secrets.

The passphrase is the one thing you have to remember. Store it in the password
manager too, as a separate item from the file.

### 2. On the new Mac: Xcode command line tools

```sh
xcode-select --install
```

### 3. Determinate Nix

`hosts/common/darwin.nix` sets `nix.enable = false`; this config deliberately
does not manage the nix installation. Install Determinate Nix, not vanilla nix:

```sh
curl -fsSL https://install.determinate.systems/nix | sh -s -- install --determinate
```

Open a new shell afterwards so `nix` is on PATH. `ids.gids.nixbld = 350` in
`hosts/common/darwin.nix` matches what this installer creates.

### 4. Import the keys

The config repo is public, so this runs before anything is cloned:

```sh
nix run github:Superd22/nixos-config#keys -- import keys-<hostname>-<date>.age
```

It asks for the passphrase, puts the SSH keys in `~/.ssh` with the right
permissions, and imports the GPG key with its trust. It refuses to overwrite a
key that is already there and different; `--force` as a second argument
replaces it.

### 5. Hostname

`build-switch` builds `darwinConfigurations.$(hostname -s)`, so the new Mac's
name has to match a directory under `hosts/`. Either rename the Mac (System
Settings > General > About > Name, or `sudo scutil --set LocalHostName
David-M3-Pro`) or copy `hosts/David-M3-Pro` to `hosts/<new-name>` and commit
it. `doctor` checks this.

### 6. Clone and run doctor

```sh
mkdir -p ~/.config
git clone git@github.com:Superd22/nixos-config.git ~/.config/nixos-config
cd ~/.config/nixos-config
nix run .#keys -- doctor
```

`doctor` proves, before activation, that:

- `hosts/<hostname>` exists;
- `id_rsa` is there, mode 600, and GitHub accepts it;
- `id_ed25519` is there, mode 600, and its public key, **derived from the
  private key** rather than read from the `.pub` file, is a recipient in
  `nix-secrets/secrets.nix`. This is the check that catches the
  `id_ed25519_agenix` mix-up;
- a GPG secret key exists for the host's `mine.user.email`.

It fails loudly with a sentence naming the missing piece, instead of an agenix
decrypt error halfway through activation.

### 7. Build and switch

```sh
nix run .#build-switch
```

Asks for sudo. The first run is long: it builds the world and installs Homebrew
via nix-homebrew (`mutableTaps = false`, `autoMigrate = true`), then all the
casks the host lists in `mine.homebrew`. Restart the terminal afterwards.

### 8. Things nix does not do for you

- **App logins.** Docker Desktop, Slack, Spotify, Steam, NordVPN, ZeroTier,
  Parsec, 1Password: all manual. Pritunl is not in that list — `wm-login`
  covers it, below.
- **Raycast.** `modules/config/raycast/` holds the scripts and quicklinks, but
  Raycast has to be pointed at that directory once, and its own settings need
  importing from a Raycast export.
- **Cloud logins.** With `mine.work.wemaintain.enable` on, `~/.aws/config`,
  the RDS CA bundle and the gcloud project are all in place after
  `build-switch`; nothing is copied from the old Mac. What is left is the
  browser: run `wm-login` once, and again whenever `withPg` starts failing
  with an SSO error. If the machine had a hand-written `~/.aws/config`, it
  is at `~/.aws/config.before-nix`.
- **The VPN.** Part of that same `wm-login`: it opens
  <https://vpn.wemaintain.io/login>, and a profile minted there — the copied
  link, or the downloaded `.tar`, which it offers by default if it is fresh in
  `~/Downloads` — is registered with the Pritunl client. Nothing comes from the
  old Mac; the profile is per machine. Connect it from the Pritunl app once it
  is added. Already have a profile, the step does nothing.
- **Monitor names.** The aerospace/betterdisplay scripts address displays by
  the literal names `Left` and `Right`. Rename them in BetterDisplay to match,
  or the ultra-wide Raycast scripts silently do nothing.
- **macOS permissions.** Accessibility for aerospace, screen recording for the
  screen-lock monitor and OBS. Granted per app in System Settings on first run.

### 9. Retiring the old Mac

Only once `doctor` passed and `build-switch` finished on the new one.

Because the identity is the same on both, nothing has to be removed from GitHub
or re-keyed in `nix-secrets`. The old disk simply has to stop existing:

1. Confirm the bundle's backup copy is where you put it in step 1.
2. Revoke what was per-machine: `~/.ssh/self_deployment` if unused, the GitHub
   App key under `~/wmtn/` (regenerable from the App's settings), AWS SSO
   sessions (`aws sso logout`), and the old Mac's VPN profile on
   <https://vpn.wemaintain.io> — the new Mac minted its own, and the old one
   stays valid until it is deleted there.
3. Sign out of iCloud, then System Settings > General > Transfer or Reset >
   Erase All Content and Settings. FileVault is on, so this is a cryptographic
   erase.

## From scratch

No old Mac, or a fork of this repo. Steps 2 and 3 above apply unchanged; the
keys are generated instead of imported.

```sh
ssh-keygen -t rsa -b 4096 -f ~/.ssh/id_rsa -C "you@example.com"      # GitHub
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519 -C "you@example.com"      # agenix
gh auth login
gh ssh-key add ~/.ssh/id_rsa.pub --title "$(hostname -s)"
gpg --quick-generate-key "Your Name <you@example.com>" ed25519 sign 0
gpg --armor --export you@example.com | gh gpg-key add -
```

Then the secrets repo. It is a private repo containing `secrets.nix` and the
`.age` files; the flake input `secrets` in `flake.nix` points at it.

```sh
gh repo create --private you/nix-secrets --clone
cd nix-secrets
cat > secrets.nix <<EOF
let
  you = "$(cat ~/.ssh/id_ed25519.pub)";
in
{
  "github-npm-token.age".publicKeys = [ you ];
}
EOF
nix run github:ryantm/agenix -- -e github-npm-token.age   # paste the token
git add . && git commit -m "first secret" && git push
```

Point `inputs.secrets.url` in `flake.nix` at the new repo, set
`mine.secrets.enable = true` in your host, and run `doctor`. If you would
rather not have a secrets repo at all, leave `mine.secrets.enable` at its
default `false` and the input is never fetched.

Once the keys exist, `nix run .#keys -- export` gives you the backup bundle;
make it now, not when the laptop is already broken.

## Later: a YubiKey

The plan above keeps one file-based identity. A hardware key slots in as a
**second recipient** for the secrets, so that either the laptop's
`id_ed25519` or the token can decrypt. That is one line in `secrets.nix`
(`age-plugin-yubikey` recipients look like `age1yubikey1...`) and one
`agenix -r` from a machine that already holds an accepted identity. Nothing in
this document changes to make room for it.

The token should stay a recovery and re-key recipient rather than the one
activation uses: agenix on darwin decrypts inside a root launchd daemon with no
terminal, and the plugin's default touch policy needs a finger on the key.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| `error: cannot fetch input 'git+ssh://…nix-secrets'` | `id_rsa` missing or not on GitHub. `doctor` says which. |
| agenix decrypt failure during activation | `id_ed25519` is not a recipient in `nix-secrets/secrets.nix`. `doctor` would have said so; the fix needs a machine that holds an accepted identity. |
| `build-switch` builds `darwinConfigurations.<something>` that does not exist | Hostname does not match a directory under `hosts/` (step 5). |
| every commit rejected / unsigned | No GPG secret key for `mine.user.email` (step 4, or `doctor`). |
| `keys import` refuses to overwrite | A different key is already at that path. Decide which one is right before `--force`. |
